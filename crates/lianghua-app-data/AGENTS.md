# 组件取舍

后续 agents 修改本组件时请继续维护本文件，只记录难以从代码理解的工程取舍；首次设计和普通 bug 修复不记，没有合适记录时不要硬写。

- 问题：全历史指标补算的一次性合并会使查询和事务内存峰值过高；解决方案选择：每累计约 131,072 行就合并提交并清空临时表；解释：以用户允许短时新增约 1GB 内存为预算，较大批次减少反复合并的开销，但行数不是硬内存上限；失败后已提交批次可由重跑覆盖。

- 问题：上市日与首条行情之间的差距可能来自停牌、恢复上市，不能认证历史截短；解决方案选择：不再按上市日或全库起点生成历史缺失问题及修复按钮，仅明确未完成的行情修复记录阻断计算；解释：真实库有大量起点差异，仅凭现有数据无法区分停牌、恢复上市与真实缺失；即使降为警告仍会诱导无依据重拉，且无法用任意天数容差证明缺失。价格衔接检测已移除，差异化分红造成的前收盘差异不能认证行情损坏，也不能保证重拉后消失。

- 问题：校验重复执行下载衔接检查或复用正式算法抽样重算，成本高且会把合法分红、当前策略和成分变化当成一致性问题；解决方案选择：只保留行情可用性、未完成修复、指数覆盖缺口、已有结果的读取失败及重算欠账；解释：下载已在写入前检查衔接并登记补救计划，行情变更与欠账同事务，结果由事务或影子表整体提交，不重复校验这些保证。跨库结果提交与清账不是同一事务，中断仍可能留下欠账，所以报告明确为待重算记录与已有结果日期的交集、完成状态待确认，不直接宣称数值错误或确定未重算；早于首个结果的待重算日期不提示，维护记录沿用本次源库快照读取；纯新增与未生成结果允许存在。每个结果库独立捕获读取错误且不自动覆盖；保留只读 4 线程、2GB 数据库缓冲预算，预算不代表进程内存上限。

- 问题：新筹码是连续状态计算，首条已保存快照不一定等于原始计算输出起点，换一天预热起点就能产生误报；解决方案选择：按用户要求从检测报告移除新旧筹码项目及对应抽样重算，不清除下载维护留下的待修复记录；解释：未保存完整初始化来源时不能保证独立回放与原计算同条件，保留已知行情改动的修复记账，避免评分误用确定过期的筹码结果。

- 问题：筹码维护期间持有原始库写连接会使其他清单更新另开独立写实例，同文件实例之间不共享目录及块缓存；解决方案选择：只读取得待修复代码后立即关闭源连接，维护返回后才短时开写连接清除完成项；解释：缩短原始库写实例的生命周期，避免空维护也触发原始库写打开和 checkpoint。

- 问题：历史行情变化触发的整股筹码重放、策略或特征版本变化触发的全量重建，与日常增量共用进度阶段时，前端会把历史维护耗时和完成数并入增量倒计时；解决方案选择：分别发布 `repair_cyq_history`、`rebuild_cyq_history` 和 `maintain_cyq_incremental`，历史重放保留自己的股票计数，进入日常增量后重新从该阶段计数；解释：阶段耗时速度不同，只有 phase 边界能让前端重置采样并分别估算，不能为了单一总进度把两类工作强行合并。

- 问题：宽表预览的 LIMIT 不能阻止关联和排序读入全历史列，rowid IN 或 CTE 半连接在行号分散时仍可能扫描宽表；解决方案选择：同一只读快照先取排序行号，按精确连续行号区间 UNION ALL 回表，再批量补展示键的指标；解释：区间过滤让存储跳过无关数据，也避免每行一次点查的查询开销，保留数据库默认资源配置。
