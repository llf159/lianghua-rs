# 组件取舍

后续 agents 修改本组件时请继续维护本文件，只记录难以从代码理解的工程取舍；首次设计和普通 bug 修复不记，没有合适记录时不要硬写。

- 问题：全历史指标补算的一次性合并会使查询和事务内存峰值过高；解决方案选择：每累计约 131,072 行就合并提交并清空临时表；解释：以用户允许短时新增约 1GB 内存为预算，较大批次减少反复合并的开销，但行数不是硬内存上限；失败后已提交批次可由重跑覆盖。

- 问题：前复权的前收盘与上一条收盘可能因差异化分红口径不同而不相等，按硬错误处理会误阻正常计算；解决方案选择：保留最近 60 个交易日衔接检查及 max(0.011 元，前收盘万分之一) 容差，但仅作非阻断提示，历史起点仅对照 max(stock_list.csv 上市日，全库历史起点) 作非阻断提示，仅明确未完成的行情修复记录阻断计算；解释：九号公司 2026-08-07 的每份实际分红 1.23852 元、除息参考价采用摊薄分红 1.22317 元，两分钱差异不能认证行情损坏，也不能保证重拉后消失。停牌、恢复上市等也会使首日偏晚，上市日与首条行情之间的差距不能认证截短，不另设任意天数容差。取较晚日期避免要求补回主动限定下载区间以前的历史。

- 问题：全库重算核验在平板上的成本过高，检查日期和字段有效性又不能验证计算结果；解决方案选择：概念/行业、相似度的已有结果抽取首日、中间交易日、末日，每日按日期参与的代码/名称哈希选最多 3 个样本，复用正式计算过程重算关键值，以 max(1e-6，重算值绝对值 × 1e-8) 比较；解释：覆盖历史不同位置并避免永远只选代码最小的股票，限制重算目标规模；相似度仍保留正式历史候选池；检测只读连接按用户要求放宽为 4 线程、2GB 数据库缓冲预算，以增加查询资源余量，该预算并不是进程内存上限。不重算全市场名次，策略、成分及资料更新造成的差异只提示，不据此判定文件损坏。

- 问题：新筹码是连续状态计算，首条已保存快照不一定等于原始计算输出起点，换一天预热起点就能产生误报；解决方案选择：按用户要求从检测报告移除新旧筹码项目及对应抽样重算，不清除下载维护留下的待修复记录；解释：未保存完整初始化来源时不能保证独立回放与原计算同条件，保留已知行情改动的修复记账，避免评分误用确定过期的筹码结果。

- 问题：筹码维护期间持有原始库写连接会使其他清单更新另开独立写实例，同文件实例之间不共享目录及块缓存；解决方案选择：只读取得待修复代码后立即关闭源连接，维护返回后才短时开写连接清除完成项；解释：缩短原始库写实例的生命周期，避免空维护也触发原始库写打开和 checkpoint。
