# 组件取舍

后续 agents 修改本组件时请继续维护本文件，只记录难以从代码理解的工程取舍；首次设计和普通 bug 修复不记，没有合适记录时不要硬写。

- 问题：全历史指标补算的一次性合并会使查询和事务内存峰值过高；解决方案选择：每累计约 131,072 行就合并提交并清空临时表；解释：以用户允许短时新增约 1GB 内存为预算，较大批次减少反复合并的开销，但行数不是硬内存上限；失败后已提交批次可由重跑覆盖。

- 问题：上市日与首条行情之间的差距可能来自停牌、恢复上市，不能认证历史截短；解决方案选择：历史起点仅对照 max(stock_list.csv 上市日，全库历史起点) 作非阻断提示，仅明确未完成的行情修复记录阻断计算；解释：不另设任意天数容差，取较晚日期避免要求补回主动限定下载区间以前的历史。价格衔接检测已移除，差异化分红造成的前收盘差异不能认证行情损坏，也不能保证重拉后消失。

- 问题：校验重复执行下载衔接检查或复用正式算法抽样重算，成本高且会把合法分红、当前策略和成分变化当成一致性问题；解决方案选择：只保留行情可用性、未完成修复、非阻断历史起点提示、指数覆盖缺口、已有结果的读取失败及重算欠账；解释：下载已在写入前检查衔接并登记补救计划，行情变更与欠账同事务，结果由事务或影子表整体提交，不重复校验这些保证。跨库结果提交与清账不是同一事务，中断仍可能留下欠账，所以只按已有结果实际覆盖的日期区间提示需要重算的结果范围，早于首个结果的待重算日期不提示；纯新增与未生成结果允许存在。每个结果库独立捕获读取错误且不自动覆盖；保留只读 4 线程、2GB 数据库缓冲预算，预算不代表进程内存上限。

- 问题：新筹码是连续状态计算，首条已保存快照不一定等于原始计算输出起点，换一天预热起点就能产生误报；解决方案选择：按用户要求从检测报告移除新旧筹码项目及对应抽样重算，不清除下载维护留下的待修复记录；解释：未保存完整初始化来源时不能保证独立回放与原计算同条件，保留已知行情改动的修复记账，避免评分误用确定过期的筹码结果。

- 问题：筹码维护期间持有原始库写连接会使其他清单更新另开独立写实例，同文件实例之间不共享目录及块缓存；解决方案选择：只读取得待修复代码后立即关闭源连接，维护返回后才短时开写连接清除完成项；解释：缩短原始库写实例的生命周期，避免空维护也触发原始库写打开和 checkpoint。
