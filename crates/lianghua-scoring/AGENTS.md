# 组件取舍

后续 agents 修改本组件时请继续维护本文件，只记录难以从代码理解的工程取舍；首次设计和普通 bug 修复不记，没有合适记录时不要硬写。

- 问题：组合策略的命中数到分值映射可非单调，窗口内未知条件若按 false 计数，会凭不完整证据产生错误分值；解决方案选择：基础评分直接保留表达式三态结果，原 scope 窗口内有未知结果时该规则不计分、不触发，以缺值计数前缀和做 O(1) 窗口判定，跟踪直接复用来源分而不再重复求值校验；解释：不猜测缺失条件的贡献，单条规则也采用相同完整窗口口径；表达式内部遵循三态逻辑，能确定为真或假的结果不属于未知。

- 问题：每个评分工作线程持有大批历史明细，写库落后时又堆积在途结果，容易放大平板内存峰值；解决方案选择：评分输入按任务预算和预热行数、规则宽度估算批次（最多128股），写库队列保留2批并另加实际对象及字符串字节配额；解释：保留 Rayon 并行与批量读取，同时以较小批次和有界队列及时反压；内存返回接口按调用契约仍保留完整结果，不受写库队列限制。

- 问题：派生依赖的全局欠账会阻止不读取该数据的手动评分；解决方案选择：门禁按本次股票池及实际加载日期（含预热与停牌尾部补足）连接已有筹码或 S_RANK 数据，仅在读到受影响的已有行时阻止；解释：缺少派生数据仍沿用空值注入约定；筹码从记账的首个变更日起失效，旧版无起点的记录按未知全历史处理，不凭空认证其早期值有效。

- 问题：全历史跟踪让只算一天也加载十几年行情，直接复用旧单事件检查点又无法还原滑动窗口排除早期事件后的状态；解决方案选择：预热取各跟踪总期限加其表达式及基础评分最大预热需求的最大值，股票池按输出区间取，评分与独立回放共用逐输出日的有限窗口语义，不再用单事件检查点续推；解释：以期限内重放换取可预测的历史范围和区间切分一致性，持久状态仅用于展示，算法版本升级使旧状态失效。

- 问题：跟踪分混入来源规则明细后，原触发与后续确认的贡献无法独立回测；解决方案选择：每条跟踪以「跟踪·名称」单列分值和稠密列编号，原规则保持原始分，场景与阶段沿用来源且总分只加一次；解释：无需复制来源表达式或虚构普通评分规则，同时让数据库与临时回测能分别评价发现和跟踪；名称须与其他计分项唯一，旧混合明细需重算。

- 问题：scope 窗口重复扫描耗时，但用浮点前缀和或滚动加减替换累加会改变舍入，影响阈值与同分排名；解决方案选择：普通 ANY/EACH/RECENT/CONSEC 使用整数滑动状态，距离 EACH 直接按原日期顺序累加；组合 ANY 用命中数单调队列且同数取最近日，组合 EACH 缓存每日基础分及 bonus 后仍按原日期顺序分别累加，最后沿用原封顶顺序；解释：只消除整数判断、重复求分及中间分配，保持分值逐位一致；每日结果按需缓存，不在缺值导致无有效窗口时提前计算所有分值，未知窗口后重建 ANY 队列。

- 问题：内存回测需要保持生产同分口径和评分原始索引，但逐日再按512股查询J值会让多年基线产生大量串行数据库往返；解决方案选择：评分索引并行排序，J按相邻日期块批量Arrow读取，仅保留实际同分成员，块达到约131072评分行或32个日期即结束，同分组并行排序后原位更新名次；解释：保持J升序、缺失靠后与代码兜底，既不重排评分实体也不让全历史J常驻；131K行／32日用于平衡扫描摊销与平板内存，单日不拆开所以并非硬上限，小股票池可能额外读取同日其他股票的J，但不纳入排序。

- 问题：研究基线和分层回测只消费评分，却仍为每股遍历全部运行时序列计算跟踪检查点签名并序列化最终事件；解决方案选择：RuleBacktest和SceneOnly模式仍完整重放跟踪、累计分值，但跳过仅供生产状态展示/落库的检查点签名和JSON，其他评分模式继续保留；解释：回测消费的是逐日得分，不使用检查点续算；省去历史字段数×天数的额外扫描，不能借此跳过跟踪评分或复用旧事件。需要检查点的调用方必须使用保留检查点的模式。

- 问题：新筹码主散年龄与买卖路径需要供历史评分使用，读取旧库时不能将缺少数据解释成零或把混合年龄当主力年龄；解决方案选择：从快照列按需注入12个独立字段，主散年龄沿用摘要行版本门禁，缺列/旧行注入未知，买卖与身份迁移分别公开；解释：同一批量/单股读取路径可复用历史表达式，无需评分时重放筹码，也不会因只新增接口就给未验收信号加分。

- 问题：Rayon 的批次初始化并不保证每线程只调用一次，逐批新开行情、筹码和相似度 DuckDB 实例会重复创建引擎线程池和缓存，现场曾出现4090个线程；解决方案选择：每轮评分各建一份读取源，批次初始化在短锁内克隆连接，SQL仍使用各自连接并行执行；解释：共享数据库实例的线程池与缓存，同时保留连接独立的查询状态，锁只覆盖克隆过程，内存返回和写库入口共用此方式；该调整针对资源膨胀，不表示已证实原生崩溃根因。

- 问题：复用评分完成断点可能混入变更后的输入或策略，而逐次校验整库内容成本过高；解决方案选择：按版本化评分语义标记、复权方式、日期范围、策略正文，以及source顶层数据库/WAL、CSV和TOML的名称、大小、修改时间生成断点键，排除结果库本身，计算前后核对，匹配时仅发送继续排名和Finish确认；解释：以元数据快照替代全库hash，其他输入库的无关变更也会保守失效，不能识别被人为保留大小和时间戳的替换；评分语义或断点布局变化须升级score-compute-stage版本标记。只跳过已确认完成的逐股评分，不恢复半轮计算。
