# 组件取舍

后续 agents 修改本组件时请继续维护本文件，只记录难以从代码理解的工程取舍；首次设计和普通 bug 修复不记，没有合适记录时不要硬写。

- 问题：组合策略的命中数到分值映射可非单调，窗口内未知条件若按 false 计数，会凭不完整证据产生错误分值；解决方案选择：基础评分直接保留表达式三态结果，原 scope 窗口内有未知结果时该规则不计分、不触发，以缺值计数前缀和做 O(1) 窗口判定，跟踪直接复用来源分而不再重复求值校验；解释：不猜测缺失条件的贡献，单条规则也采用相同完整窗口口径；表达式内部遵循三态逻辑，能确定为真或假的结果不属于未知。

- 问题：每个评分工作线程持有大批历史明细，写库落后时又堆积在途结果，容易放大平板内存峰值；解决方案选择：评分输入每批 32 股，写库队列只缓存 2 批；解释：保留 Rayon 并行与批量读取，同时以较小批次和有界队列及时反压；内存返回接口按调用契约仍保留完整结果，不受写库队列限制。

- 问题：派生依赖的全局欠账会阻止不读取该数据的手动评分；解决方案选择：门禁按本次股票池及实际加载日期（含预热与停牌尾部补足）连接已有筹码或 S_RANK 数据，仅在读到受影响的已有行时阻止；解释：缺少派生数据仍沿用空值注入约定；筹码从记账的首个变更日起失效，旧版无起点的记录按未知全历史处理，不凭空认证其早期值有效。

- 问题：事件身份受历史触发节奏影响，且递归指标和任意历史修订都可能改变当前锚点，只回看 ttl 天或只按文件末日续算会产生与全量不同的分数；解决方案选择：跟踪与原评分共用每股历史输入和原始分值，按股核对日历、实际运行字段和来源分前缀签名后，只推进检查点之后的事件，前缀不一致则该股全量回放；解释：以继续读取历史、重建指标及线性签名核验的成本换取可修订历史下的确定性，不宣称整个排名任务为纯新增日复杂度；跟踪分合并到原规则明细并沿用其场景和 stage，避免伪造新规则或因后续观察自动改变既有场景定义。
