# 组件取舍

后续 agents 修改本组件时请继续维护本文件，只记录难以从代码理解的工程取舍；首次设计和普通 bug 修复不记，没有合适记录时不要硬写。

- 问题：把截面聚合塞入单股 Runtime 会混淆股票与时间两个维度，并迫使每个指标单独实现公式；解决方案选择：PanelRuntime 负责 CS_* 的股票轴与分组，普通子表达式继续交给原 Runtime 沿时间求值，明确区分标量、市场共享序列和逐股矩阵；解释：复用既有时间函数及空值规则，CS_RANK 返回逐股百分位而非已有 GRANK/LRANK 的时间窗口名次；CS_VAR/STD 使用样本口径，原 STD 的总体口径保持不变，配置中需要显式换算。

- 问题：将普通发现贡献置零时，依赖正贡献的起点会连带关闭仍需保留的后续确认；解决方案选择：允许 source 与 start 同时存在，以 start 决定起点、source 保留场景和阶段归属；解释：不让来源表达式命中自动替代所有原有正分起点，也不通过极小非零分维持触发。自定义起点独立保存，来源条件修改时需同步维护。

- 问题：仅限制观察期会让已得分事件无限保留，而直接截断单事件回放又会让更早的事件占位影响窗口内起点；解决方案选择：ttl 限制观察，max_age 从起点限制包含保分的总寿命（缺省等于 ttl，且不得小于 ttl），每个输出日独立按最近 max_age 个市场交易日回放；解释：窗口内仍保持单事件、不续期，窗口外事件不再压制窗口内发现，以有限历史依赖换取单日、区间与分段计算的一致性；用并行窗口状态共享表达式准备，单日只建立一个窗口，长区间成本随期限增加。

- 问题：跟踪表达式编译时若把赋值内联到引用处，`A1 := A0 + A0` 这类链式复用会让 AST 随赋值次数指数膨胀，26 行表达式即产生约 6700 万节点、编译耗时 69 秒，而 `ScoreConfig::validate` 在每次载入与保存时都会重新编译，足以卡死配置修改；解决方案选择：`TrackExpression` 保留赋值语句，按声明顺序逐条求值，只把不依赖当日跟踪上下文（AGE、冻结值及其派生的局部量）的赋值在整段历史上预计算为共享序列，其余语句每天结合事件上下文重算；解释：以每天多执行几条语句换取编译的线性时间（160 行内联链 0 毫秒、486 个节点），代价是必须用 `derived_locals` 维护"哪些局部量随天变化"，因此不要为了减少运行时变量而恢复内联。

- 问题：跟踪逐日复制历史窗口、重建运行时会放大分配成本，但把所有判断都改成单点计算会破坏含事件变量的窗口函数语义；解决方案选择：无剩余函数调用的预处理表达式复用单日求值器和局部变量槽，含事件变量的函数继续在共享历史窗口上求值；通用数值及三态序列转换以 Cow 借用同类型数据，仅广播、类型转换或明确取得所有权时分配；解释：共享窗口保留算子所需历史，缺值由统一三态求值传播，局部变量槽每次求值先标记未赋值，防止前一天的局部量遮蔽当天输入；运行时缓存只在每股的 prepared 对象内复用，不跨股票共享。

- 问题：已有事件续算或整段未触发时仍准备冻结表达式，会计算根本用不到的历史指标；解决方案选择：首次实际建立起点时才准备 capture，并在同股 prepared 对象内缓存，后续新起点按各自日期重新取冻结值；解释：准备缓存与起点冻结值分离，既省掉未使用的指标计算，也避免把上一个起点的值错误用于新事件。
