# 组件取舍

后续 agents 修改本组件时请继续维护本文件，只记录难以从代码理解的工程取舍；首次设计和普通 bug 修复不记，没有合适记录时不要硬写。

- 问题：MSN 缺竞价等单股响应被拒绝后，等待统一 60 秒重试会延误其他可用源补齐；解决方案选择：每轮单股任务记录已尝试来源，响应拒绝或请求失败后立即按各源限速/冷却选择尚未尝试的源，全部可用源失败才进入 60 秒重试；解释：避免反复选中同一失败源，同时保留平台独立冷却、暂停取消和上一份可用基准，MSN 的 09:50 门槛仍生效。

- 问题：MSN 沪深交易所元数据声明延迟 15 分钟，开盘前五分钟无法立即用于补齐，而且分钟量口径有偏差；解决方案选择：北京时间到 09:50 后才允许当天沪深股票的第三个 MSN 源参与调度，开关随轮询更新以覆盖此前排队的任务，默认启动间隔 500ms，HTTP 429/5xx 独立冷却 60 秒并翻倍间隔（上限 2 秒），使用该源时在量比状态中显示近似基准；解释：20 分钟门槛覆盖 15 分钟延迟与完整五分钟窗口，解析仍检查实际窗口连续性，时间门槛不等于数据必然齐全。MSN 首次需搜索 ID 再取图表，较保守间隔减少额外请求压力；标的 ID 按代码缓存。盘中当前值仍来自实时累计量，近似历史量不冒充实时行情；腾讯与东财先可用时仍优先选择它们。

- 问题：全市场分时补齐没有请求间隔会触发腾讯 HTTP 501，固定五个交易日期又会误拒停牌股票；解决方案选择：五日均量按行情日期前最近五根有效且有成交的 qfq 日线取数，8 个后台线程动态分配腾讯与东财，两个平台初始请求间隔均为 100ms，各平台遇到 HTTP 5xx/429 独立冷却 60 秒并将本平台间隔翻倍（最大 2 秒），手动暂停立即使排队/等待任务失效，保留同日已补齐基准与高点；解释：两平台无错误时理论合计每秒最多 20 次启动，5500 只调度下限约 4.6 分钟，HTTP 耗时及冷却会增加实际耗时；连接/超时/响应体读取错误只保留单股失败并按原计划重试，不暂停整个源，因为没有 HTTP 状态无法推断限流，网络出口故障不应阻塞其余股票，HTTP 5xx 独立冷却 60 秒并降速，让另一平台继续补齐；8 并发限制同时在途请求，100ms 间隔限制启动速率，失败返回很快时只减并发不能代替间隔与冷却，不能保证供应商不再限流；已发出的请求最多等待 12 秒结束但不会写入已失效任务。停止轮询 60 秒后不再执行排队请求，恢复时保留同日可用数据；09:30–09:35 基准仍须覆盖完整窗口，补齐前禁用量比新高提示。

- 问题：本地日历可能过期，休市日的旧行情也可能落在固定交易时段内；解决方案选择：按北京时间连续交易时段检查，要求有效价格行情中严格过半数为当天、本交易时段且距现在不超过 180 秒，日历仅在行情无法确认交易时辅助解释；解释：多数样本避免单股时间异常，180 秒平衡供应商延迟、全市场分批抓取与停更识别，跨午休必须重新取得下午行情；正常盘中与非交易时段无需额外读盘或网络请求。

- 问题：模板预热缓存命中前重复编译，简单条件反复计算全历史，而直接缩短预热又会改变指标结果；解决方案选择：先按模板、股票/板块、相关文件修改时间与大小及北京时间日期查缓存；按股票完成全部模板后释放运行数据，无函数条件只求最新点，含函数模板保留完整求值并隔离赋值；解释：减少重复编译与临时内存，同时保留 EMA/SMA 原预热长度，避免以改变初值传播和结果换取速度。

- 问题：实时监控的五日涨幅与量比均量分别读日线，前者还对每股全历史排序且长期不刷新；解决方案选择：全市场监控共用一条聚合 SQL 和按仓库、行情日期缓存的日线基准，沿用量比的 60 秒刷新间隔；收盘价用 Top-N 保留最近六根，均量取行情日前最近五根有效成交日线；解释：一次扫描同时取得两类基准，减少重复读库与排序，代价是日线更新最多等待 60 秒；用 struct 包装空收盘价以保留日线位置，停牌和日历缺失不再阻止已有五根日线形成均量基准。详情页单股量比继续使用单股查询，避免为一只股票扫描全市场。
