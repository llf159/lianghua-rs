# 组件取舍

后续 agents 修改本组件时请继续维护本文件，只记录难以从代码理解的工程取舍；首次设计和普通 bug 修复不记，没有合适记录时不要硬写。

- 问题：Appender flush 不提交事务，长周期评分明细会在事务内持续累积内存；解决方案选择：持久暂存表每 32 批提交一次并复用组内 Appender，排名分别在独立事务写入影子表，最后原子替换正式表；解释：固定提交粒度平衡未提交数据峰值与事务/写入器重建开销，中途失败仍保留正式数据。排名保留单条窗口 SQL，避免按日期分块重复扫描；但排名输出和增量回插仍有各自未提交行的内存峰值，不能把短事务理解为进程硬内存上限。排查时可对比 SELECT tag, memory_usage_bytes FROM duckdb_memory() 与 ps -o rss= -p <pid>，不要仅凭数据库缓冲统计判断总内存。

- 问题：全量评分替换时把主键、二级索引和表交换放在同一事务会叠加索引构建内存；解决方案选择：影子表主键先提交，交换事务只做表替换，命名索引在交换后逐条创建；解释：降低同时持有的索引内存，代价是交换后中断可能留下缺少命名索引的正式表；主键和数据仍完整，下次 init_result_db 补索引，不清表。

- 问题：筹码重建增加计算线程会放大每线程历史快照内存，固定少量线程又无法利用多核；解决方案选择：增量每批 8 股，全量使用 available_parallelism()，每批 max(ceil(32 / 线程数), 1) 股，队列缓存 2 批，DuckDB 缓冲预算 2GB、数据库线程 4；解释：以约 32 股同时计算平衡多核吞吐与快照峰值，超过 32 核时至少每线程 1 股，内存仍会增长；2GB 仅约束 DuckDB 缓冲，不是进程总内存上限。可用 pidstat -t -u -p <pid> 1 与 ps -o rss= -p <pid> 比较线程使用和峰值。

- 问题：全量筹码写入逐批提交成本高，单个 Arrow Appender 调用线程又会成为吞吐瓶颈；解决方案选择：临时库从同一 DuckDB 实例克隆 2 个写入连接，每连接每组达到 32 批、16 股或约 25 万分桶行后提交，全部写完再写元数据、建索引和替换正式库；解释：两个连接平衡并行追加吞吐与事务内存倍增，合计未提交分桶行预算约 50 万，单批可能超过阈值；失败只丢弃临时库，增量写正式库仍保留原子事务。

- 问题：写线程逐条准备 Arrow 列和检查点 JSON 时，计算线程会因队列满而等待；解决方案选择：全量重建由计算线程准备批次，写连接只执行 SQL、追加和提交，增量与单股修复保留原始入口；解释：用计算并行度分担准备成本，代价是准备期间短暂同时持有快照和 Arrow 列；队列仍限 2 批，优化吞吐时需一并观察 RSS。

- 问题：单股筹码修复若删除后重建正式库索引，内存成本会随全库规模增长；解决方案选择：增量与单股修复保留索引，已有数据但缺索引时初始化不自动补建；解释：维护成本随变更行数增长，以缺索引库的部分查询变慢为代价，避免修复入口触发大型全库索引重建。可用 SELECT index_name FROM duckdb_indexes() WHERE table_name = 'cyq_chen_snapshot' 检查是否缺索引。

- 问题：下载中断需要保留修复计划，但原有公共计算门禁把差异化分红的前收盘差异和旧结果历史当作坏行情证据，容易与当前检查面板不一致；解决方案选择：保留下载流程的持久补救计划和派生重算记账，公共计算门禁仅要求已有前复权行情且没有 pending_stock_repair 明确未完成的修复记录，不再用历史起点及已删除的覆盖、数值、重复与全市场缺日检查阻断计算；解释：检查面板与计算入口保留同一未完成修复门禁；历史起点受停牌、恢复上市影响，复权衔接受差异化分红影响，两者只提示，不阻断。全库历史起点之前的主动限制下载区间不要求补回，完全没有行情的股票不属于截短检查。

- 问题：修复行情后最大日期可能不变，新旧筹码还共用旧版待修复列表；解决方案选择：行情事务持久标记行业、评分、相似度的待重算日期范围，只有覆盖该范围的成功重算才能清除；筹码分别记账每个模型完成状态，两种已有模型均完成才删除共用记录；解释：最新一天补算不能覆盖历史复权变更，一个模型修好也不能让另一模型吞掉待修复项。下次行情变更同时清除相应完成状态，避免关闭软件后旧结果被当成正确结果。

- 问题：普通增量也持久记录待计算区间后，把任何待重算记录都当成旧结果失效会阻断正常依赖计算；解决方案选择：评分和相似度的依赖门禁仅在待重算区间与对应已保存结果日期重叠时阻断，缺失结果及纯新增日期不据此阻断；解释：新增日期尚未算出与覆盖历史造成旧值失效含义不同，保留下载中断记账并遵循后续缺失允许存在的约定。

- 问题：只查询状态或预览却用默认写模式打开文件，会在原写实例仍存活时生成独立写实例并触发落盘，旧缓存可能覆盖新目录；解决方案选择：状态、预览、选股及监控统一使用 open_db_readonly，真正写入清单和数据的入口才开写连接；解释：只读实例不能 checkpoint，读取未落盘 WAL 也不会写回文件，配合下载/派生维护阶段的连接所有权交接避免同文件独立写实例重叠。
