# 组件取舍

后续 agents 修改本组件时请继续维护本文件。

- 本 crate 负责持久化、数据库结构、领域配置和数据到表达式运行时的转换。
- 评分结果库的建表、批量写入、数据库排名与补排名统一位于 `data::scoring_store`。
- 可以依赖 `lianghua-model` 的共享类型，禁止依赖 scoring、download、backtest 或应用层 crate，确保依赖无环。
- 不在 data 中实现评分规则计算或把评分序列构造成结果行。
- 只运行 `cargo test -p lianghua-data`，不要因此触发全 workspace 测试。
- 改变筹码初始化或逐日迁移语义时必须提升 `CYQ_CHEN_SCHEMA_VERSION`，强制旧库完整重建，禁止在旧状态上混用新算法续算。
- 新筹码 schema 4 将原始精度分桶和有限待确认批次放入每股唯一的 `cyq_chen_checkpoint`，与历史快照同事务提交；展示值仍四舍五入。策略指纹包含 schema 版本，避免旧算法或缺失后验状态被静默续算。检查点只保存最新状态，历史修订应走单股重建。
- 场景排名随评分批次写入暂存表，再按原排序键在数据库计算全市场排名，避免 Rust 常驻全量场景明细。
- 问题：评分结果写库曾把整个长周期运行放进一个 DuckDB 事务（Appender 每 32 批 `flush()` 一次），而 `flush()` 只把数据推进事务、不提交，几十个批次的明细行、暂存表和排名写入结果全部留在 transaction-local storage 里，内存随批次单调上涨，8 年全区间仅 `rule_details` 就有约 5600 万行；解决方案选择：正式表在替换前完全不动，长周期写入改为持久暂存表 + **每 32 批一个短事务提交**（Appender 仍是每批 `flush()`，32 批后统一 commit，Appender 每个提交组只重建一次），summary/scene 排名各用一条原窗口 SQL 在独立短事务里从暂存表写入 `*_write_shadow`，最后一个短事务只做「drop 正式表 → rename 影子表」，增量区间则在最后事务里删区间并从影子表回插；解释：DuckDB 里未提交的修改必须留在内存直到 commit，与 `memory_limit` 无关，按固定批数提交既切断了「跑得越久涨得越多」的链条（上界固定 32 批，约等于原来的 flush 粒度），又不会退化成逐批提交带来的事务/Appender 重建开销。排名**不按交易日分块**：那是排名阶段的单次峰值而不是跨批次累积，DuckDB 的 window 本身支持 spill，分块只会引入对暂存表的重复扫描；同理 summary/scene 仍各跑一条 SQL。正式三张表直到最后一步才被替换，所以中途打断或崩溃只会留下可丢弃的暂存表（下次运行开头 `DROP TABLE IF EXISTS` 清掉），不会出现半成品数据库。
- 问题：全量替换的收尾曾把「3 个主键 + 3 个二级索引 + 表交换」放进同一个事务，索引内存全部挂到 commit 才释放，60 批（约 1500 万行）实测峰值 2.27GB，按 8 年全区间（约 8700 万行）线性外推会到十几 GB；解决方案选择：主键在影子表上单独提交创建，交换事务只做 drop+rename（纯元数据），命名索引在交换提交之后再逐条建（每条索引各自一个事务）；解释：把「一次持有全部索引」改成「一次只持有一条索引」，同一负载峰值降到 1.10GB，交换与 commit 从 7.3s+10.0s 降到 0.009s+1.2s。崩溃恢复仍然安全：交换前崩溃只影响影子表；交换后、建索引前崩溃会留下「有主键、缺命名索引」的正式表，`init_result_db` 只会补建索引、不会清表（`ensure_result_table_schema` 见到主键即返回），数据不受影响。
- 已知下界（未解决）：DuckDB 未提交行不参与 spill，所以任何「一次性写 N 行」的事务都会常驻 N 行内存。实测 60 批（约 1500 万行）时：增量路径最终事务（删区间 + 从影子表回插 + commit）峰值 2.26GB，且 commit 阶段独占 23s；summary/scene 排名插入各自把整表输出压在内存里（场景 22M 行全区间量级更高）。这些都不是跨批次累积，但按全区间外推仍可能撑爆进程；要再降只能把排名插入按交易日分块提交到影子表（安全，只影响暂存层），以及给增量替换加「区间外行数 < 本次新增行数」时走影子表复制+交换的分支（原子，但会把区间外数据重写一遍）。下次排查内存时可用 `SELECT tag, memory_usage_bytes FROM duckdb_memory()` 对比 `BASE_TABLE` 与 `ps -o rss= -p <pid>`：RSS 随阶段上涨而 `duckdb_memory()` 各 tag 近似为 0，说明内存卡在未提交事务/索引构建上，而不是缓冲池。
- 写库暂存表是固定名字（`score_summary_stage`、`scene_details_stage`、`score_summary_write_shadow`、`rule_details_write_shadow`、`scene_details_write_shadow`），每次运行开始时先清空重建、失败时尽力删除；并发发起第二次排名计算会互相清理暂存表，因此仍依赖单次运行（当前只有前端 `busyAction` 层面禁止并发）。
- 新筹码重建与增量统一每批 8 股、队列缓存 2 批，平衡历史分桶内存峰值与批量读写吞吐；逐日演化不变，避免重建时每个线程积累 128 股快照。
- 新筹码写线程失败会连带关闭发送通道，汇总结果必须优先返回写线程的具体原因，避免 `sending on a closed channel` 掩盖数据库错误；显式计算中断仍通过 Abort 回滚。小批次计算复用 Rayon 任务内的行情连接，检查点写入复用预编译语句，不通过扩大在途快照量提速。
- 全量新筹码重建只向空临时库写入，每个 8 股批次独立提交，最后才写元数据、建索引并替换正式库；全量大事务的 flush 不释放事务生命周期内的积累，因此失败时丢弃临时库，不再要求临时库整体回滚。增量写正式库仍保留原子事务。
- 全量重建计算最多 4 个 Rayon 工作线程，临时写库限制 512MB 缓冲和 2 个数据库线程，给行情、历史分桶及界面留出空间，避免两层并行与数据库默认内存预算一起挤占进程；这是吞吐与移动端内存峰值的折中，不是进程总内存硬上限。
- 正式新筹码库初始化和全量重建前清理严格匹配 `.cyq_chen.db.rebuild-<pid>-<timestamp>.tmp` 的残留及其 WAL/溢出目录；清理与整个重建过程共用目录文件锁，拿不到锁时初始化跳过清理、第二个重建直接报忙。锁文件保留，不能删除后重新创建造成跨进程锁失效；崩溃由系统释放锁，下一次初始化再清理，不依赖 PID 或残留文件年龄猜测任务存活。
- 问题：Rust 1.94 的标准文件锁未实现 Android，且 `TryLockError` 的显示文本隐藏底层错误；解决方案选择：Android 使用原生非阻塞 `flock`，其他平台继续用标准库，并展开底层错误和锁文件路径；解释：保留跨进程互斥和文件关闭自动释放语义，区分锁忙与平台/I/O 故障。
- 问题：下载状态读取间接初始化新筹码库，加锁清理失败会阻断整个状态页面；解决方案选择：元数据查询不再初始化、迁移或清理，缺失表按空数据或缺失策略快照处理；解释：将查询与维护分开，真正的维护入口仍显式初始化并保留重建锁保护。
- 问题：指数字段与指标列若用连字符连接，会与表达式减法冲突；解决方案选择：使用 `I_列名`、`I300_列名` 等下划线写法，原 `I` 等简写仍表示指数涨跌幅；解释：表达式词法原生支持下划线标识符，读取时按指数代码和交易日取 `stock_data` 的原始列值，避免改变减法语义。
- 新增或改名 `STOCK_DATA_RUNTIME_FIELDS`、`RUNTIME_INDEX_COLS` 与指标列（`ind.toml`）时必须同步前端 `ui/lianghua_web/src/shared/expressionValidation.ts` 的 `KNOWN_EXPRESSION_IDENTIFIERS`：表达式回测“参数研究”的自动识别只能靠这份白名单区分“可用字段”与“待扫描参数”，漏同步的字段会被替换成常数。
- 数据层文件按功能拆分并保持“测试跟随被测文件”：`data/cyq_chen/{mod,config,bars,simulate,buckets,test_support}`、`data/cyq_chen_data/{mod,store,compute,maintain,test_support}`；测试写在各自文件的 `#[cfg(test)] mod tests` 内，跨文件共用的夹具放同目录 `test_support.rs`，公共 API 仍由各 `mod.rs` 汇总导出，禁止再恢复单一 `tests.rs`。
