# 组件取舍

后续 agents 修改本组件时请继续维护本文件，只记录难以从代码理解的工程取舍；首次设计和普通 bug 修复不记，没有合适记录时不要硬写。

- 问题：混合年龄特征不能还原差异化出库后的初始来源，旧检查点又没有这份账本；解决方案选择：在每个成本桶按main/retail仅保存两项初始残留，随对应出库比例和归一化迁移，新成交及其后验不改变初始来源；检查点用可选字段兼容旧数据，缺失时来源保持不可用，耗尽的旧桶才恢复已知空来源，不升级整个库版本或强制全市场重建；解释：用两个质量值获得模型内精确来源而不新增完整年龄维度，旧库存不被伪装为零残留；原有价格、归属和特征算法未变，需来源分解时从原模拟起点重放，不能由中性换手乘积补猜复杂模型。

- 问题：额外筹码模型先收集全部历史分桶再汇总会与绘图模型叠加内存，缺少历史股本又无法证明固定总体假设成立；解决方案选择：重放引擎共用逐日输出入口，绘图调用收集快照，对照调用立即汇总并释放；结果显式返回总体未经核实，不以当前股本快照或价格变化推断历史无事件；解释：降低额外历史分桶占用并保留相同计算语义，表达式历史和绘图快照仍随输入增长；初始未知量只描述固定总体下的初始化残留，不冒充股本事件后的全部未知成本。

- 问题：中性筹码参照若同时更换初值或价格网格，模型差异会混入初始化变化，旧引擎的初始成本估计又不能当成已知成本；解决方案选择：三模型共用原生引擎和初始化，在等概率参照中按包含预热的实际换手精确计算初始存活量，并从均价和获利盘的已知部分扣除同一初始分布；解释：保留可比性，同时用未知比例及获利盘范围披露初始成本不确定性；该分解只适用于固定总体的等概率参照，不套用到持有人差异出库模型，也不改变正式库的模型版本。

- 问题：跨股票指标既有同日共享结果，也有各股排名和组内统计，硬编码字段与逐股重复存储都会限制用户配置；解决方案选择：`ind.toml` 用 scope 区分逐股、市场和横截面，通用长表保存后两者，读取按配置发现；跨股票范围统一按市场日历补空并沿用时间表达式引擎，输入按64股分批，局部量只在单个跨股票指标内有效；解释：动态名称不再要求字段注册，日历补空可使窗口依赖不受停牌压缩影响；64平衡批次开销和输入内存，但截面中间矩阵仍随历史与同时保留的序列数增长。有限窗口按依赖链保守累加预热、独立分支取最大值，EMA/SMA/BARSLAST 则保留完整历史重放，不以任意预热近似初值。

- 问题：跨股票计算按子表达式和64股反复查询、转换相同输入；解决方案选择：增量仍先物化必要日期及列，股票列表和出勤矩阵也从该读取会话查询；指数按整轮共享一份日期序列，股票原始输入矩阵合计不超过64MiB时一次流式加载并跨指标复用，超过预算则逐表达式整市场流式读取；解释：64MiB约束额外原始矩阵，以日常短窗口复用换取少量常驻内存，避免长历史按全部字段缓存挤占平板内存；预算不是进程总内存上限，表达式结果矩阵仍随历史增长，流式读取每次只组装当前股票，指数不按股票复制。缓存仅在本轮存在，不跨行情写入复用。

- 问题：按字段禁用价格会误拒C/O等相对表达式，而截面聚合后再相除不能消除不同股票的复权因子；解决方案选择：静态传播股票及各指数独立的价格尺度，允许同股比值、同尺度比较及其局部变量和逐股指标依赖，要求进入CS_*的参数及最终跨股输出消除尺度；解释：不读取行情比较数值，无法证明尺度抵消的价格函数组合明确报错，不能把CS_MEAN(C)/CS_MEAN(O)误判为复权无关。

- 问题：横截面结果按每股每日落长表，全历史单个事务会累积过多未提交数据；解决方案选择：计算前提交待修复起点并隐藏后续日期，逐指标求值、按128股 Arrow 短事务追加，只保留后续指标仍依赖的结果，全部完成后统一发布配置签名及完成日期；解释：以计算或写入失败后重跑覆盖该区间换取及时释放矩阵、减少逐行编码并约束未提交写入；读入口同时校验配置签名和待修复范围，不会暴露部分新结果。保存批量从64放宽到128股，以较多未提交数据换取减少提交和写入器重建；输入读取仍按64股。单批行数仍随历史天数增长，128股不是进程固定内存上限，Appender flush 也不能代替事务提交。

- 问题：全市场预检会重复读取并解析每股数百 KB 的续算 JSON，串行检查拖慢日常增量；解决方案选择：不再全库扫描最新状态或比较逐股历史末日，只在实际续算读取时统一校验分桶、后验库存及特征状态，不可用则按原结果起点整股重放，并将该股旧历史替换与本轮增量放在同一事务；局部修复和增量都只有收到显式 Finish 才向正式库原子发布，计算批次先在独立暂存库提交以保留断点，完整重建仍先写临时库再替换；解释：健康股票只解码一次，无新增行情直接结束；未使用的坏检查点等下次续算再修复，已知历史行情修订依靠下载持久修复清单，不靠日常全库扫描发现。不可用状态重放失败则正式结果保持原样，已提交暂存批次可续算，不用舍入展示表补续算状态；下载已提交阶段仍依靠持久欠账重试，不宣称下载全过程是跨库事务。

- 问题：Appender flush 不提交事务，长周期评分明细会在事务内持续累积内存；解决方案选择：持久暂存表每 64 批提交一次并复用组内 Appender，排名分别在独立事务写入影子表，最后原子替换正式表；解释：提交粒度从32放宽到64批，以较多未提交数据换取减少事务提交与写入器重建开销，中途失败仍保留正式数据。排名保留单条窗口 SQL，避免按日期分块重复扫描；但排名输出和增量回插仍有各自未提交行的内存峰值，不能把短事务理解为进程硬内存上限。排查时可对比 SELECT tag, memory_usage_bytes FROM duckdb_memory() 与 ps -o rss= -p <pid>，不要仅凭数据库缓冲统计判断总内存。

- 问题：全量评分替换时把主键、二级索引和表交换放在同一事务会叠加索引构建内存；解决方案选择：影子表主键先提交，交换事务只做表替换，命名索引在交换后逐条创建；解释：降低同时持有的索引内存，代价是交换后中断可能留下缺少命名索引的正式表；主键和数据仍完整，下次 init_result_db 补索引，不清表。

- 问题：全量及局部修复若按线程维持约32股读取窗口，在小线程数下每组只有几股，全市场会产生大量小行情查询；简单扩大整块读取又会把整组历史行情同时留在内存；解决方案选择：全量及局部修复固定按128股形成流式读取块，`load_batch_streaming` 利用 `ORDER BY ts_code, trade_date` 逐股组装并按 `ts_code` 切换，当前股票算完立即转 Arrow 并送入有界队列，不收集块内 PreparedBatch；增量仍需并发读取续算检查点，继续按 max(ceil(64 / 线程数), 1) 股分组整块读取；解释：全市场行情SQL从数百次降到几十次，同时每线程只保留当前股票及一个Arrow结果批次，128股主要平衡查询开销、任务数和尾部负载；全量队列4批、增量队列2批及2个正式库写连接不变；4GB仅约束DuckDB缓冲，不是进程总内存上限。可用 pidstat -t -u -p <pid> 1 与 ps -o rss= -p <pid> 比较线程使用和峰值。

- 问题：分桶卖出规则常引用该分桶的 `RATE*` 序列，逐交易日求值会落到表达式引擎的整段历史重算，使每个价格桶重复构造完整向量；解决方案选择：卖出规则不依赖动态筹码总量或比例时，按分桶价格边界惰性预计算每日合并后的主力/散户卖出倾向并复用，依赖这些动态字段时保留逐日原路径；解释：同一桶的 `RATE*` 只由成本价和行情决定，可在股票内部安全复用，代价是每个活跃价格桶多保留一份历史倾向缓存，而无活跃筹码的空桶不计算。当前回退以价格桶为单位：任一卖出规则引用 `MAIN_CHIP_RATIO`、`MAIN_CHIP_TOTAL` 或 `RETAIL_CHIP_TOTAL` 时，同桶其他本可缓存的 `RATE*` 规则也会逐日重算；后续应拆分静态与动态规则、分别合并倾向，避免一条动态规则关闭整桶优化。

- 问题：全量筹码写入逐批提交成本高，单个 Arrow Appender 调用线程又会成为吞吐瓶颈；解决方案选择：临时库从同一 DuckDB 实例克隆 2 个写入连接，每连接每组达到 64 批、32 股或约 50 万分桶行后提交，全部写完再写元数据、建索引和替换正式库；解释：保留两个连接，事务三个阈值均翻倍，以较多未提交数据换取减少提交和写入器重建开销；合计未提交分桶行目标约100万，检查发生在接收下一批之前，单批可能超过阈值，因此不是硬上限；失败保留已提交的临时库批次供续算，增量写正式库仍保留原子事务。

- 问题：DuckDB 1.4.4 默认 16MiB 自动 checkpoint 阈值会被大批次事务估算大小反复触发，遍历增长中的行组并序列化元数据，使提交逐渐变慢；解决方案选择：新筹码全量临时库、评分暂存写入、市场／横截面指标分批保存共用 `BulkWriteSettings`，工作期间设 `checkpoint_threshold = '256MB'`，原提交边界不变，成功收尾显式 CHECKPOINT，再恢复原阈值，失败也恢复；解释：以较大 WAL 换取减少重复 checkpoint，收尾落盘计入当前操作，避免只将成本转移到下一项计算；阈值不是 WAL 或进程内存硬上限，不关闭 WAL/同步。新筹码增量与旧筹码的大事务不套此设置；`LIANGHUA_CYQ_WRITE_PROFILE=1` 可区分计算转列、队列等待、追加、flush、提交及最终索引和落盘。

- 问题：新筹码先收集整股历史快照再生成 Arrow，会同时保留历史分桶对象与列式缓冲，历史 pending 又只用于最后一日续算；解决方案选择：全量重建和指定股票历史重放都在计算线程逐日转列，仅暂留最后一个未舍入快照，计算成功后校验并序列化该日完整检查点，再追加最后一行；日常增量仍需读取续算状态并保留完整快照入口，绘图继续共用同一列构造器；解释：让两条全历史计算路径共用预构造与并行策略，避免写线程成为修复瓶颈，同时不改变日常续算状态语义、舍入展示列、检查点精度、模型归属和事务发布规则。

- 问题：筹码时长特征让检查点成为每股数百 KB 的字符串，逐股 INSERT OR REPLACE 的 DuckDB MERGE 更新拖慢写线程并阻塞计算队列；解决方案选择：每批按股票和复权类型删除旧检查点，再用 Appender 追加整批并 flush，沿用调用方事务统一提交；解释：实际 5480 股检查点副本上，8 股逐次替换约 1.07 秒，批量删除再 Appender 追加约 6.8 毫秒；flush 仅把追加数据交给事务，不提前提交，失败仍与摘要、分桶一起回滚。

- 问题：单股筹码修复若删除后重建正式库索引，内存成本会随全库规模增长；解决方案选择：增量与单股修复保留索引，已有数据但缺索引时初始化不自动补建；解释：维护成本随变更行数增长，以缺索引库的部分查询变慢为代价，避免修复入口触发大型全库索引重建。可用 SELECT index_name FROM duckdb_indexes() WHERE table_name = 'cyq_chen_snapshot' 检查是否缺索引。

- 问题：下载中断需要保留修复计划，但原有公共计算门禁把差异化分红的前收盘差异和旧结果历史当作坏行情证据，容易与当前检查面板不一致；解决方案选择：保留下载流程的持久补救计划和派生重算记账，公共计算门禁仅要求已有前复权行情且没有 pending_stock_repair 明确未完成的修复记录，不再用历史起点及已删除的覆盖、数值、重复与全市场缺日检查阻断计算；解释：检查面板与计算入口保留同一未完成修复门禁；历史起点受停牌、恢复上市影响，复权衔接受差异化分红影响，两者只提示，不阻断。全库历史起点之前的主动限制下载区间不要求补回，完全没有行情的股票不属于截短检查。

- 问题：修复行情后最大日期可能不变，新旧筹码还共用旧版待修复列表；解决方案选择：行情事务持久标记行业、评分、相似度的待重算日期范围，成功重算只扣除实际完成的日期，分段完成保留其余区间；筹码分别记账每个模型完成状态，两种已有模型均完成才删除共用记录；解释：最新一天补算不能覆盖历史复权变更，一个模型修好也不能让另一模型吞掉待修复项。下次行情变更同时清除相应完成状态，避免关闭软件后旧结果被当成正确结果。

- 问题：筹码维护状态只暴露策略变更，特征版本升级或已有空库同样会从历史起点重建，但调用方无法在开始前选择正确的历史维护阶段；解决方案选择：状态同时返回 `feature_changed`，下载入口将策略变更、特征变更及已有空库一并视为全量历史维护；解释：不能等底层已经发出计算进度后再猜阶段，提前判断可避免先做无意义的指定股票修复，并让进度从第一帧起使用正确的时间口径。

- 问题：普通增量也持久记录待计算区间后，把任何待重算记录都当成旧结果失效会阻断正常依赖计算；解决方案选择：评分和相似度的依赖门禁仅在待重算区间与对应已保存结果日期重叠时阻断，缺失结果及纯新增日期不据此阻断；解释：新增日期尚未算出与覆盖历史造成旧值失效含义不同，保留下载中断记账并遵循后续缺失允许存在的约定。

- 问题：只查询状态或预览却用默认写模式打开文件，会在原写实例仍存活时生成独立写实例并触发落盘，旧缓存可能覆盖新目录；解决方案选择：状态（包括筹码元数据）、预览、选股及监控统一使用 open_db_readonly，真正写入清单和数据的入口才开写连接；解释：只读实例不能 checkpoint，读取未落盘 WAL 也不会写回文件，配合下载/派生维护阶段的连接所有权交接避免同文件独立写实例重叠。

- 问题：用当前总市值和复权股价比例回推历史会带入当前股本结构，而成交额与换手率只能反推流通口径；解决方案选择：历史推测市值统一使用 AMOUNT（千元）/ TOR（百分数）/ 1000，保留 TOTAL_MV_YI 接口名，缺失、非正或非有限输入返回空值，不沿用前日或当前市值；解释：结果为按当日成交均价计价的流通市值，并非收盘价总市值，保留变量名避免破坏现有表达式，但历史筛选、上涨金额、行业/概念加权和相似度的数值口径随之改变，旧派生结果需要重新计算。

- 问题：下载请求的休市日边界会让实际行情全量重算仍无法清账，而单区间记账又不能保存分段完成的历史；解决方案选择：待重算表按组件保存多个不重叠区间，旧版单主键表在写事务内升级，读取与清账范围按前复权行情和该组件旧结果的实际日期裁剪；解释：允许分别完成历史与增量，保留旧结果独有日期以免行情删减后把旧值误判为有效，纯新增或缺失结果继续不作为旧结果失效门禁。

- 问题：增量筹码的独立只读实例不参与写实例的事务及数据块管理，长字符串续算状态在并发读写中可能读到不一致内容，且旧版 duckdb-rs 1.4.4 的 try_clone 不延长主数据库句柄寿命（升级后的1.20000.0已改为共享所有权）；解决方案选择：增量计算与写入从同一主连接克隆，计算线程仅执行查询，主连接放在 Mutex 中供任务初始化短时克隆，写线程使用 scoped thread，并保持主连接存活至所有计算和写入结束；解释：只读打开能防止查询入口落盘，但不能代替同文件并发读写的共享实例。克隆时的锁不覆盖计算，保留并行吞吐；写事务在计算队列关闭后提交，计算连接看到提交前的续算状态，异常退出也先结束借用句柄的线程。

- 问题：筹码仅按股票记录欠账会把晚期行情变更扩展到早期快照，两个模型又可能分别完成维护；解决方案选择：共享清单继续保留，但分别记录新旧模型的首个变更日期，已完成模型遇到新变更从新日期开始，旧版未知起点保持未知；解释：保留中断恢复及模型独立完成语义，为评分提供日期门禁依据，不因另一模型的更早欠账扩大已修复模型的影响区间。

- 问题：跟踪状态独立落文件会在排名写入中断时留下新分数配旧事件，日期索引又依赖计算时的日历；解决方案选择：事件检查点和共享日历随评分批次写入独立暂存表，与正式总榜、规则明细和场景榜在最终事务中一起发布；解释：每次只保留本次参考日的事件快照，避免历史事件全量常驻，历史回放仍由行情重建；保存日历可使日历修订后的旧快照保持可解释，而不是用新日历错误翻译旧索引。

- 问题：相似榜算法升级后，页面虽拒绝旧榜，但S_RANK与实时监控可能继续读取旧汇总排名；解决方案选择：算法版本在数据组件统一定义，汇总视图、评分注入及监控均要求生效配置版本匹配，未知或旧版本按缺失排名处理，原始结果保留供重算前核对；解释：同一版本门槛贯穿展示和表达式，不删除用户数据，也不以旧版名次冒充新版收益排序。

- 问题：基础成本若直接复用身份模型的完整分布，会把填充初值和身份出库反馈带入K/U；解决方案选择：V1用独立质量账本，共用原生成交分配与网格代码，所有股本变化按比例继承，不读取或要求手动事件，VOL/TOR跳变与缺口只作非阻断数据质量提示，旧身份模型保留；解释：K/U已经表示当前流通总体中的比例，统一比例继承意味着股本变化本身不改变二者，之后只需按当天实际换手迁移；提示不能证明真实事件或新增股份成本，未知量仍只保留无法定位的起点前库存。

- 问题：`ZHANG` 只表示涨跌停幅度，且创业板与科创板可能同值，表达式无法据此可靠区分板块；解决方案选择：新增运行时数值字段 `BOARD_ID`，主板=1、创业板=2、科创板=3、北交所=4，按股票代码前缀判定，无法识别时为空；解释：固定编码供条件表达式使用，不把 ST 或未知市场静默并入主板，也不让板块字段参与 K/U 迁移；历史板块状态仍须有独立来源，当前字段不能冒充历史上市板块档案。

- 问题：全量新筹码重建遇到 I/O 故障后丢弃临时库会损失所有已提交计算，而仅凭末日续算可能混入历史修订前的结果；解决方案选择：固定保留 `.cyq_chen.db.resume.tmp` 及 WAL，股票完成标记与摘要、分桶和检查点同事务提交，包含无输出股票；按行情库及 WAL、股票资料、日历和指标配置的大小与修改时间，加计算配置、策略版本和区间校验输入代次，仅跳过同代次已提交股票，最终仍整体替换正式库；解释：不缩小原有批次以保留写入吞吐，失败最多需要重做尚未提交的事务及计算队列；文件代次校验避免扫描整库历史，代价是仅元数据改变也会保守重算，不能识别刻意保持大小和时间的外部修改。进度仍在原数据盘上，WAL 或数据库本身损坏无法保证恢复；恢复打开失败保留现场，不自动删库。文件沿用 `.tmp` 后缀以排除目录导出，且不匹配旧随机重建文件的清理规则。

- 问题：逐股指标补算逐行构造动态参数有重复分配，而按整股历史转列会额外占用长历史缓冲；解决方案选择：DOUBLE 指标暂存表每 8192 行构造 Arrow，沿用列名解析、空值和原 UPDATE 提交边界；基础行情的 DECIMAL 列继续通过逐值 Appender 转换，只把固定字段中间值改为栈数组；解释：8192 是四个 DuckDB 向量的折中批量，以少量列缓冲换取减少参数分配，不累积跨股结果；Arrow 数据块不能直接把 DOUBLE 当作目标 DECIMAL，避免改变既有精度和溢出处理。

- 问题：增量与局部修复的大事务在源库读取失败后丢掉整轮计算，直接逐批提交正式库又会暴露半轮结果；解决方案选择：共用 `.cyq_chen.db.maintenance.tmp` 和维护目录锁，暂存每组达到32股、64批或约50万分桶行即提交，完成标记、整股替换标记与结果同事务，Abort／断连也提交已收到的完整批次，全部股票完成且收到 Finish 后只读挂载暂存库、一次事务发布；按源库及正式结果库/WAL的大小和修改时间、基础资料与配置内容及计算区间校验代次；解释：沿用全量写入的组大小以平衡提交开销与意外退出时的重做量，输入变化保守重算，小文件原样重写不丢进度，正式发布失败仍有计算结果可重试；最终发布仍有事务内存峰值。暂存库与原数据同盘，不承诺抵抗该盘本身损坏，也不绕过源库校验和错误。历史修复发布后先清该阶段欠账，再进入增量，避免增量失败后重复历史修复改变续算输入。

- 问题：间歇性 I/O 或校验和读取失败会中断行情计算，盲目重连会丢失临时行情表或事务快照，重放流式回调又可能重复写入；解决方案选择：共用读取重试入口，初次失败后最多重试3次，依次等待250ms、500ms、1000ms，仅重试 I/O／校验和错误并排除明确的权限、路径不存在、磁盘满等错误；普通读取每次重新准备查询并丢弃未完成结果，流式读取按已成功交付的股票排除重读，回调错误直接返回，Arrow 使用可返回错误的 step 而非会 panic 的迭代器；解释：合计1.75秒退避给短暂存储故障恢复机会，同时限制永久损坏带来的阻塞；沿用原连接以保留共享实例、临时表及事务语义，不自动回滚调用方事务，不重试计算或写事务，也不把持续损坏当作成功。
