# 组件取舍

后续 agents 修改本组件时请继续维护本文件，只记录难以从代码理解的工程取舍；首次设计和普通 bug 修复不记，没有合适记录时不要硬写。

- 问题：混合年龄特征不能还原差异化出库后的初始来源，旧检查点又没有这份账本；解决方案选择：在每个成本桶按main/retail仅保存两项初始残留，随对应出库比例和归一化迁移，新成交及其后验不改变初始来源；检查点用可选字段兼容旧数据，缺失时来源保持不可用，耗尽的旧桶才恢复已知空来源，不升级整个库版本或强制全市场重建；解释：用两个质量值获得模型内精确来源而不新增完整年龄维度，旧库存不被伪装为零残留；原有价格、归属和特征算法未变，需来源分解时从原模拟起点重放，不能由中性换手乘积补猜复杂模型。

- 问题：额外筹码模型先收集全部历史分桶再汇总会与绘图模型叠加内存，缺少历史股本又无法证明固定总体假设成立；解决方案选择：重放引擎共用逐日输出入口，绘图调用收集快照，对照调用立即汇总并释放；结果显式返回总体未经核实，不以当前股本快照或价格变化推断历史无事件；解释：降低额外历史分桶占用并保留相同计算语义，表达式历史和绘图快照仍随输入增长；初始未知量只描述固定总体下的初始化残留，不冒充股本事件后的全部未知成本。

- 问题：中性筹码参照若同时更换初值或价格网格，模型差异会混入初始化变化，旧引擎的初始成本估计又不能当成已知成本；解决方案选择：三模型共用原生引擎和初始化，在等概率参照中按包含预热的实际换手精确计算初始存活量，并从均价和获利盘的已知部分扣除同一初始分布；解释：保留可比性，同时用未知比例及获利盘范围披露初始成本不确定性；该分解只适用于固定总体的等概率参照，不套用到持有人差异出库模型，也不改变正式库的模型版本。

- 问题：跨股票指标既有同日共享结果，也有各股排名和组内统计，硬编码字段与逐股重复存储都会限制用户配置；解决方案选择：`ind.toml` 用 scope 区分逐股、市场和横截面，通用长表保存后两者，读取按配置发现；跨股票范围统一按市场日历补空并沿用时间表达式引擎，输入按64股分批，局部量只在单个跨股票指标内有效；解释：动态名称不再要求字段注册，日历补空可使窗口依赖不受停牌压缩影响；64平衡批次开销和输入内存，但截面中间矩阵仍随历史与同时保留的序列数增长。有限窗口按依赖链保守累加预热、独立分支取最大值，EMA/SMA/BARSLAST 则保留完整历史重放，不以任意预热近似初值。

- 问题：跨股票增量按64股和子表达式重复查询时，DuckDB 的顺序扫描使短窗口维护仍反复访问历史行情；解决方案选择：实际读取起点晚于行情首日时，在专用读取连接内用临时 `stock_data` 表保存输出及预热区间的必要列，复用读取器并按子表达式选择列，同时保留该区间的指数输入；解释：用一次区间物化和临时表空间换取后续扫描缩小，不增加正式库索引或修改持久行情；完整历史重放不物化，避免复制整段历史。临时表及截面矩阵仍随读取区间增长，64股并非总内存上限；进度显示输出及实际读取日期，方便区分日常增量和历史修复。

- 问题：横截面结果按每股每日落长表，全历史单个事务会累积过多未提交数据；解决方案选择：计算前提交待修复起点并隐藏后续日期，逐指标求值、按64股 Arrow 短事务追加，只保留后续指标仍依赖的结果，全部完成后统一发布配置签名及完成日期；解释：以计算或写入失败后重跑覆盖该区间换取及时释放矩阵、减少逐行编码并约束未提交写入；读入口同时校验配置签名和待修复范围，不会暴露部分新结果。单批行数仍随历史天数增长，64股不是进程固定内存上限，Appender flush 也不能代替事务提交。

- 问题：全市场预检会重复读取并解析每股数百 KB 的续算 JSON，串行检查拖慢日常增量；解决方案选择：不再全库扫描最新状态或比较逐股历史末日，只在实际续算读取时统一校验分桶、后验库存及特征状态，不可用则按原结果起点整股重放，并将该股旧历史替换与本轮增量放在同一事务；局部修复和增量都只有收到显式 Finish 才提交，完整重建仍先写临时库再替换；解释：健康股票只解码一次，无新增行情直接结束；未使用的坏检查点等下次续算再修复，已知历史行情修订依靠下载持久修复清单，不靠日常全库扫描发现。不可用状态重放失败则本轮全部回滚，不用舍入展示表补续算状态；下载已提交阶段仍依靠持久欠账重试，不宣称下载全过程是跨库事务。

- 问题：Appender flush 不提交事务，长周期评分明细会在事务内持续累积内存；解决方案选择：持久暂存表每 32 批提交一次并复用组内 Appender，排名分别在独立事务写入影子表，最后原子替换正式表；解释：固定提交粒度平衡未提交数据峰值与事务/写入器重建开销，中途失败仍保留正式数据。排名保留单条窗口 SQL，避免按日期分块重复扫描；但排名输出和增量回插仍有各自未提交行的内存峰值，不能把短事务理解为进程硬内存上限。排查时可对比 SELECT tag, memory_usage_bytes FROM duckdb_memory() 与 ps -o rss= -p <pid>，不要仅凭数据库缓冲统计判断总内存。

- 问题：全量评分替换时把主键、二级索引和表交换放在同一事务会叠加索引构建内存；解决方案选择：影子表主键先提交，交换事务只做表替换，命名索引在交换后逐条创建；解释：降低同时持有的索引内存，代价是交换后中断可能留下缺少命名索引的正式表；主键和数据仍完整，下次 init_result_db 补索引，不清表。

- 问题：筹码重建增加计算线程会放大每线程历史快照内存，固定少量线程又无法利用多核；解决方案选择：增量每批 8 股，全量使用 available_parallelism()，每批 max(ceil(32 / 线程数), 1) 股，队列缓存 2 批，DuckDB 缓冲预算 2GB、数据库线程 4；解释：以约 32 股同时计算平衡多核吞吐与快照峰值，超过 32 核时至少每线程 1 股，内存仍会增长；2GB 仅约束 DuckDB 缓冲，不是进程总内存上限。可用 pidstat -t -u -p <pid> 1 与 ps -o rss= -p <pid> 比较线程使用和峰值。

- 问题：全量筹码写入逐批提交成本高，单个 Arrow Appender 调用线程又会成为吞吐瓶颈；解决方案选择：临时库从同一 DuckDB 实例克隆 2 个写入连接，每连接每组达到 32 批、16 股或约 25 万分桶行后提交，全部写完再写元数据、建索引和替换正式库；解释：两个连接平衡并行追加吞吐与事务内存倍增，合计未提交分桶行预算约 50 万，单批可能超过阈值；失败只丢弃临时库，增量写正式库仍保留原子事务。

- 问题：写线程逐条准备 Arrow 列和检查点 JSON 时，计算线程会因队列满而等待；解决方案选择：全量重建由计算线程准备批次，写连接只执行 SQL、追加和提交，增量与单股修复保留原始入口；解释：用计算并行度分担准备成本，代价是准备期间短暂同时持有快照和 Arrow 列；队列仍限 2 批，优化吞吐时需一并观察 RSS。

- 问题：筹码时长特征让检查点成为每股数百 KB 的字符串，逐股 INSERT OR REPLACE 的 DuckDB MERGE 更新拖慢写线程并阻塞计算队列；解决方案选择：每批按股票和复权类型删除旧检查点，再用 Appender 追加整批并 flush，沿用调用方事务统一提交；解释：实际 5480 股检查点副本上，8 股逐次替换约 1.07 秒，批量删除再 Appender 追加约 6.8 毫秒；flush 仅把追加数据交给事务，不提前提交，失败仍与摘要、分桶一起回滚。

- 问题：单股筹码修复若删除后重建正式库索引，内存成本会随全库规模增长；解决方案选择：增量与单股修复保留索引，已有数据但缺索引时初始化不自动补建；解释：维护成本随变更行数增长，以缺索引库的部分查询变慢为代价，避免修复入口触发大型全库索引重建。可用 SELECT index_name FROM duckdb_indexes() WHERE table_name = 'cyq_chen_snapshot' 检查是否缺索引。

- 问题：下载中断需要保留修复计划，但原有公共计算门禁把差异化分红的前收盘差异和旧结果历史当作坏行情证据，容易与当前检查面板不一致；解决方案选择：保留下载流程的持久补救计划和派生重算记账，公共计算门禁仅要求已有前复权行情且没有 pending_stock_repair 明确未完成的修复记录，不再用历史起点及已删除的覆盖、数值、重复与全市场缺日检查阻断计算；解释：检查面板与计算入口保留同一未完成修复门禁；历史起点受停牌、恢复上市影响，复权衔接受差异化分红影响，两者只提示，不阻断。全库历史起点之前的主动限制下载区间不要求补回，完全没有行情的股票不属于截短检查。

- 问题：修复行情后最大日期可能不变，新旧筹码还共用旧版待修复列表；解决方案选择：行情事务持久标记行业、评分、相似度的待重算日期范围，成功重算只扣除实际完成的日期，分段完成保留其余区间；筹码分别记账每个模型完成状态，两种已有模型均完成才删除共用记录；解释：最新一天补算不能覆盖历史复权变更，一个模型修好也不能让另一模型吞掉待修复项。下次行情变更同时清除相应完成状态，避免关闭软件后旧结果被当成正确结果。

- 问题：普通增量也持久记录待计算区间后，把任何待重算记录都当成旧结果失效会阻断正常依赖计算；解决方案选择：评分和相似度的依赖门禁仅在待重算区间与对应已保存结果日期重叠时阻断，缺失结果及纯新增日期不据此阻断；解释：新增日期尚未算出与覆盖历史造成旧值失效含义不同，保留下载中断记账并遵循后续缺失允许存在的约定。

- 问题：只查询状态或预览却用默认写模式打开文件，会在原写实例仍存活时生成独立写实例并触发落盘，旧缓存可能覆盖新目录；解决方案选择：状态（包括筹码元数据）、预览、选股及监控统一使用 open_db_readonly，真正写入清单和数据的入口才开写连接；解释：只读实例不能 checkpoint，读取未落盘 WAL 也不会写回文件，配合下载/派生维护阶段的连接所有权交接避免同文件独立写实例重叠。

- 问题：用当前总市值和复权股价比例回推历史会带入当前股本结构，而成交额与换手率只能反推流通口径；解决方案选择：历史推测市值统一使用 AMOUNT（千元）/ TOR（百分数）/ 1000，保留 TOTAL_MV_YI 接口名，缺失、非正或非有限输入返回空值，不沿用前日或当前市值；解释：结果为按当日成交均价计价的流通市值，并非收盘价总市值，保留变量名避免破坏现有表达式，但历史筛选、上涨金额、行业/概念加权和相似度的数值口径随之改变，旧派生结果需要重新计算。

- 问题：下载请求的休市日边界会让实际行情全量重算仍无法清账，而单区间记账又不能保存分段完成的历史；解决方案选择：待重算表按组件保存多个不重叠区间，旧版单主键表在写事务内升级，读取与清账范围按前复权行情和该组件旧结果的实际日期裁剪；解释：允许分别完成历史与增量，保留旧结果独有日期以免行情删减后把旧值误判为有效，纯新增或缺失结果继续不作为旧结果失效门禁。

- 问题：增量筹码的独立只读实例不参与写实例的事务及数据块管理，长字符串续算状态在并发读写中可能读到不一致内容，且 duckdb-rs 1.4.4 的 try_clone 不延长主数据库句柄寿命；解决方案选择：增量计算与写入从同一主连接克隆，计算线程仅执行查询，主连接放在 Mutex 中供任务初始化短时克隆，写线程使用 scoped thread，并保持主连接存活至所有计算和写入结束；解释：只读打开能防止查询入口落盘，但不能代替同文件并发读写的共享实例。克隆时的锁不覆盖计算，保留并行吞吐；写事务在计算队列关闭后提交，计算连接看到提交前的续算状态，异常退出也先结束借用句柄的线程。

- 问题：筹码仅按股票记录欠账会把晚期行情变更扩展到早期快照，两个模型又可能分别完成维护；解决方案选择：共享清单继续保留，但分别记录新旧模型的首个变更日期，已完成模型遇到新变更从新日期开始，旧版未知起点保持未知；解释：保留中断恢复及模型独立完成语义，为评分提供日期门禁依据，不因另一模型的更早欠账扩大已修复模型的影响区间。

- 问题：跟踪状态独立落文件会在排名写入中断时留下新分数配旧事件，日期索引又依赖计算时的日历；解决方案选择：事件检查点和共享日历随评分批次写入独立暂存表，与正式总榜、规则明细和场景榜在最终事务中一起发布；解释：每次只保留本次参考日的事件快照，避免历史事件全量常驻，历史回放仍由行情重建；保存日历可使日历修订后的旧快照保持可解释，而不是用新日历错误翻译旧索引。

- 问题：相似榜算法升级后，页面虽拒绝旧榜，但S_RANK与实时监控可能继续读取旧汇总排名；解决方案选择：算法版本在数据组件统一定义，汇总视图、评分注入及监控均要求生效配置版本匹配，未知或旧版本按缺失排名处理，原始结果保留供重算前核对；解释：同一版本门槛贯穿展示和表达式，不删除用户数据，也不以旧版名次冒充新版收益排序。
