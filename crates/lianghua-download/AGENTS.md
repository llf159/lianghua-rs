# 组件取舍

后续 agents 修改本组件时请继续维护本文件，只记录难以从代码理解的工程取舍；首次设计和普通 bug 修复不记，没有合适记录时不要硬写。

- 问题：股东增减持接口限额为每分钟 100 次，通用配置可能高于该额度，精确间隔也可能因请求到达时间波动触限；解决方案选择：该接口请求间隔至少 625 毫秒（每分钟 96 次），同时遵守更严格的通用限速；解释：留出少量时间余量以降低边界触限概率，代价是下载速度略低于额度上限，其他客户端共享额度时仍可能触限。

- 问题：停止请求可能长时间等待限频、重试休眠或未返回的 HTTP 请求；解决方案选择：限频及重试等待每 100ms 检查停止标记，Tushare 连接超时 10 秒、整次请求超时 60 秒；解释：等待可及时结束，已发出的阻塞 HTTP 请求仍等待返回或超时，60 秒为大响应和较慢网络留出余量；停止后不安排下一批请求，未提交事务回滚，先前提交结果保留。

- 问题：复权补救整段覆盖会把市场指标dirty_from拉到历史起点，日常增量因此变成全市场重算；解决方案选择：行情替换不对市场指标比较历史数值或记历史欠账，统一在追加后只登记已发布末日之后的日期；下载自动维护若发现旧欠账、配置或元数据要求覆盖已发布历史则明确报错，留给手动指标补算；解释：按用户业务口径，历史覆盖不驱动市场指标追偿，相对价格表达式也不因取整差异重算；真实历史输入修订需用户手动重建，显式删除仍保留失效标记。首次无已发布结果时仍允许初始化全历史。

- 问题：跨股票聚合需要等待同日其他股票和逐股派生指标完成；解决方案选择：按 scope 分为逐股下载阶段与整轮提交后的市场／横截面阶段，后者按用户配置顺序计算，可引用此前声明的指标；解释：执行阶段由数据维度决定，名称不保留给内置指标，也不禁止某几个市场字段作为输入；依赖跨股票结果的逐股公式须选择横截面范围，避免下载顺序决定数值。

- 问题：指数下载完成事件曾晚于市场／横截面指标计算，进度界面只能把新增计算塞回不准确的指数阶段；解决方案选择：指数行情先发布完成，再进入独立的 `panel_indicators` 阶段；解释：跨股票指标依赖指数输入已提交，但不能在用户视野中冒充指数下载的一部分，阶段顺序必须与真实依赖顺序一致。

- 问题：下载分段提交或先删后补时，等到整轮结束才记录修复清单会留下源行情已变化、旧结果仍被当作可用的中断窗口；解决方案选择：前复权行情删除、单股写入、按日写入与相应清单共用事务，追加新日期记录后续待计算区间，覆盖或补写已有历史再记录筹码待修复股票并重置模型完成状态；解释：事务失败两者一同回滚，已提交阶段中断则保留记录供下次继续；评分和相似度按非复权基础字段的实际行差异记账，筹码按包含价格及指标的实际行差异维护续算基准；相同输入重复下载不重置维护状态，新增与删除行也参与对比。单股覆盖区间延至该股已有末日，按日覆盖包含旧数据中被删除、上游未再返回的代码，避免遗漏连续状态计算的影响。

- 问题：duckdb-rs 1.4.4 的独立 Connection::open 不共享数据库实例，同文件两个独立写实例先后 checkpoint 会覆盖彼此的目录和数据块；解决方案选择：概念维护入口消费并关闭下载源库连接后再重建，借用源连接的股票下载阶段不执行概念维护；解释：通过所有权交接保证清单清除的新写实例不会和旧下载实例重叠，避免只靠 CHECKPOINT 而仍留下旧实例缓存；首次、补全、增量入口都走同一交接过程。

- 问题：前复权价格按分取整后反算涨幅会随复权基准变化，自动补救先删历史又无法识别纯价格变化，导致概念/行业表现反复全量重建；解决方案选择：股票涨幅保留行情源返回的 pct_chg，价格和 change 仍沿用原取整口径；单股替换在同一事务比较旧表与暂存表落库精度下的日期及 pct_chg、amount、tor，仅为概念记录实际输入变更范围，按日覆盖只记当日；自动复权补救与针对性完整修复都先持久登记计划，拉取成功才在写入事务里替换旧行情，不再提前删除旧行；解释：概念权重来自成交额/换手率，与复权价格无关，也没有跨日递推。保留旧输入增加每只补救股票一次区间查询，但避免全市场历史重算；待补救计划继续阻断中断后的派生计算。旧版按复权价格取整反算的涨幅可能与源涨幅不同，首次重新下载仍需按实际差异补算；不自动清除已有待重算欠账，以免漏掉真实修正。数据源涨幅与按分取整的 close/pre_close 比值可能不同，这是刻意保留源涨幅精度。

- 问题：针对性完整修复先删历史再回填，单股输入对比只剩新行，可达历史会被整体记为评分／相似度欠账，而日常计算只覆盖结果库末日之后，历史欠账再也清不掉；解决方案选择：修复同样保留旧行情，由单股写入事务按组件输入口径比较后再替换，只有筹码续算按该股待补救计划的起点保守标记；解释：修复未完成由待补救计划阻断派生计算，拉取失败不丢旧数据；删改行和新增行都参与对比，补回缺失日期或修正真实输入仍从首个差异日期记到已有末日，纯复权价格变化的修复不再制造评分欠账。

- 问题：覆盖请求的日期范围不等于输入实际变化范围，重复下载会制造全历史欠账；解决方案选择：仅在本次写入范围内用双向 EXCEPT ALL 按组件输入口径比较新旧行情行，按股票的首个差异日期开始标记，筹码也保存该起点；解释：增加局部写入对比成本，换取不因相同输入否定手动完成的结果；含递推状态的影响仍延伸到已有末日，未知起点的旧记录继续保守处理。

- 问题：股票复权会改变绝对价格及价格派生指标，但用户的业务口径不据此要求重算评分等结果；解决方案选择：评分及相似度的行情变更记账只比较日期、涨幅、成交量、成交额、换手率和资金流等非复权基础字段，不比较 OHLC、前收盘、价差及指标列；概念仅比较日期、涨幅、成交额、换手率，筹码另维护续算价格基准；解释：避免自动复权补救制造评分历史欠账，非复权基础输入修订及增删行仍记账，策略／指标配置变化沿用手动重算流程，不由覆盖下载的价格差异推断评分失效。

- 问题：日常增量下载被历史概念欠账扩展成全量重建，没有新交易日时也会反复自动追偿；解决方案选择：下载后概念维护只重算本轮实际新增的日期区间，无新交易日直接结束，历史欠账保留给检查页和手动重算入口；解释：保证每日流程的工作量随新增日期而非历史长度增长，代价是历史修订不再由后续一次普通下载自动消化。

- 问题：历史补全、指数下载和断点股票补救分批提交时会重复触发默认小阈值 checkpoint；解决方案选择：这些批量阶段复用数据组件 BulkWriteSettings 的 256MB 阈值，原提交粒度及修复记账不变，结束显式落盘并恢复配置，错误也恢复；解释：以较大 WAL 换取减少重复落盘，范围在市场／横截面计算及源库连接交接之前结束；按日增量仍保留整段原子事务，不把它拆成短事务。针对性逐股修复仍保留原有显式 checkpoint 边界。

- 问题：把季度数仅用于近期重刷仍会在首次下载或缺失股票时从 2000 年补全，公告日窗口还可能夹带更早报告期；解决方案选择：基本面的 N 个季度直接限定整轮下载范围，以结束日期所在季度之前最近 N 个已结束季度为报告期范围，覆盖旧调用传入的历史开始日期；按公告日查询的财报在写入前再按 end_date 筛选，非财报事件和每日股本从同一起点同步至结束日期；解释：16 个季度表示四年的报告期，当前未结束季度不计入，尚未披露的数据不保证存在；旧数据和旧同步记录保留，范围之外不再自动补缺。股东人数仍按独立日期区间同步。分红接口不支持日期范围，仍整段请求后本地过滤；主营构成仍只保留最多100行，其他接口触顶二分。

- 问题：公司数据按接口串行、逐股提交不能利用独立接口额度，事务过多；解决方案选择：每批股票数等于通用下载线程数，把批内股票的不同接口任务放进同一个线程池并发请求，保留按接口独立限频；单连接一次提交本批全部成功窗口及完成记录，沿用256MB checkpoint阈值，进度仅在批次提交后按已处理股票推进；解释：总请求并发不超过线程数，缓存限制在一批股票的各接口响应，以一定内存和批次等待换取更少事务；抓取失败保留该接口旧数据，成功接口可提交，写入失败则回滚当前整批并终止，此前批次保留。接口无权限后跳过后续该接口并将全轮股票标为存在失败；进度表示已处理而非全部成功，不再假定13个接口顺序执行。

- 问题：主营业务构成全历史触及100行上限后递归补全会消耗额外请求，而更多历史明细的信息增量有限；解决方案选择：按用户要求，fina_mainbz 每个待下载区间显式 limit=100，只保留最多100行并直接提交及登记该区间已同步，不因触顶二分补全，也不再使旧100行完成记录失效；解释：以主动舍弃部分明细换取更低请求量，完成记录表示已执行这项截取策略，不保证该区间财报明细穷尽；仍遵守所选季度的下载范围，其他接口继续检查截断并拆分。

- 问题：公司下载与行情并发后，Rayon 线程默认读取全局停止标记会误响应行情的取消；解决方案选择：创建公司下载线程池时捕获当前任务停止上下文，在线程整个生命周期内局部绑定；解释：基本面与股东人数分别响应自己的停止请求，线程池结束自动释放上下文。
