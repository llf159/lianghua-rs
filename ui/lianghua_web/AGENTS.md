# 组件取舍

后续 agents 修改本组件时请继续维护本文件。

- Tauri 适配层直接依赖各 `lianghua-app-*` UI 能力 crate，并通过 data/download/provider 等后端 crate 获取底层契约。
- 禁止重新引入 `lianghua-app`、`lianghua-engine` 或类似聚合门面隐藏真实依赖。
- Rust 侧改动只检查 `cargo check -p app`；前端改动按实际涉及范围验证，不运行无关全量测试。
- Linux 桌面端启动时仅在检测到 Snap 宿主环境后清理 Snap 注入的 GTK/GIO 模块变量，避免系统 WebKit 误加载 Snap 内的 glibc，同时不影响普通终端中用户显式设置的 GTK 环境。
- 宽表需要同时支持表内横向滚动和随页面纵向悬浮表头时，将悬浮表头放在横向滚动容器外并同步 `scrollLeft`；不要让横向 `overflow` 成为原始 sticky 表头的滚动祖先。
- 总榜、场景榜和相似榜的冻结识别区统一使用 50px 排名列与 120px 股票列，股票列内名称在上、代码在下，以较小横向占用保留滚动时的个股上下文。
- 问题：详情页历史排名接口返回空结果时，状态类型只允许数组却曾写入 `null`，既破坏 TypeScript 严格检查，也会使“已加载”判断继续重复请求；解决方案选择：统一写入空数组；解释：空数组准确表达已加载但没有排名，并保持展示层以空列表渲染的既有口径。
- 问题：通用进度条的 10% 最小填充会夸大低进度，增加时间统计后固定宽度统计格也可能挤出容器；解决方案选择：确定进度按真实比例填充，仅未知进度保留动画占位，统计格允许收缩；解释：保持进度读数与视觉长度一致，并复用现有自适应网格容纳预计时间。
- 问题：相似榜按批次上报，等待期间拿不断增长的耗时重算平均速度会让预计剩余反而上升；解决方案选择：仅在任务、阶段或完成量/总量变化时更新采样时间并按阶段累计平均重估，重复轮询保留原估计，期间按时钟倒计时且不低于零；解释：区分真实进度反馈与界面刷新，下一批反馈再校正预计时间。
- 问题：全量策略明细随主回测响应进入前端会在 Tauri 交付和 React 状态更新时形成多份大对象；解决方案选择：主响应只接收摘要，明细由回测阶段预先计算并逐策略落临时缓存，点击策略名只读取对应缓存文件；解释：点击不承担样本计算，同时避免全量明细跨端传输和前端常驻。
- 问题：横向表格容器使用双轴 `overscroll-behavior: contain` 会在自身没有纵向滚动空间时吞掉触屏纵向手势；解决方案选择：只在横轴限制滚动越界，纵轴允许向页面或模态框滚动链传递，并声明双轴平移手势；解释：保留表内横向控制，同时让自然展开表格区域可以直接拖动外层页面，悬浮表头仍由外层纵向滚动驱动。
- 问题：全局规则用 `!important` 将普通表格设为随页面全部展开，导致详情页固定高度的前日排名、桌面端相似股票以及相关性规则概览、两两相关和 Pearson 矩阵失去内部滚动并撑宽平板页面；解决方案选择：仅为这些明确限高的表格以页面限定选择器恢复内部双轴滚动，并给研究卡片和容器设置 `min-width: 0`；解释：保留普通表格和窄屏内容的页面滚动，同时避免长列表或宽指标表撑开详情侧栏和研究结果页。
- 问题：策略触发明细的触发股票表位于 Portal 内，因而不匹配原先依赖 `.strategy-trigger-page` 祖先的滚动覆盖规则；解决方案选择：直接以表格类名恢复其限高和双轴内部滚动；解释：Portal 改变 DOM 祖先关系，保留页面级普通表格展开的同时，触发明细仍与其他限高表格使用同一滚动方式。
- 问题：桌面路由曾静态导入全部页面，且 Rollup 默认会把 `manualChunks` 指定页面的依赖递归并入页面 chunk，构建后的入口因此仍会首屏预载详情、监控、管理和研究页面资源；相关性页面挂载时还自动按规则聚合扫描结果库；解决方案选择：桌面业务页面统一按路由延迟加载，构建启用 `onlyExplicitManualChunks` 防止共享依赖被页面 chunk 吞并，相关性日期范围、规则名称及触发计数改为用户点击后再加载；解释：非当前页面及研究数据都不是首屏必需内容，按需加载可缩小启动资源并避免大表扫描，同时让用户区分“加载规则统计”和“运行相关性研究”两个成本阶段。
- 问题：相关性研究页为同时塞下多张系数表、矩阵和正交卡片，把正文压到 9–11px，明显小于其他页面的 12–14px，且顶部 hero 占比过大；解决方案选择：整页字号按一档上移（9→11、10→12、11/12→13、13→14、15→16），hero 去掉边框底色并把标题降到 `clamp(18px,1.5vw,22px)`、删除“核心组说明”占位卡；解释：数据量再大也应先保证可读性，表格本就自带滚动，不应靠缩小字体换取密度，hero 只承担状态与标题。
- 问题：限高内部滚动的表格滑到顶部/底部后继续滚动会带动整页，而横向展开表又是页面滚动的一部分，两者需要统一口径；解决方案选择：只在已用 `body .xxx-table-wrap` 显式恢复限高双轴滚动的表格（维度研究结果表、详情子卡/场景概览表、策略触发明细、筹码分箱、数据库预览、自选观察、策略/资产差异表体等自身不符合 `table-wrap` 命名但同样限高的滚动区）上补 `overscroll-behavior: contain`，保持 App.css 对普通表格的横轴越界限制与纵轴 `auto` 不变；解释：真实存在纵向滚动空间时限制滚动链安全且符合预期，而横向展开表没有纵向空间，继续沿用纵轴 `auto` 以免吞掉触屏纵向手势。
- 问题：表达式回测的主结果曾挂在“详情 modal”上，单 combo 时 modal 默认关闭导致运行后结果区空白；解决方案选择：表达式回测拆成独立页面 `ExpressionBacktestPage`，结果常驻页面，modal 只保留正式策略详情、分层样本与个股详情；解释：主结果不应依赖浮层开关状态，拆页后场景/排名回测页也不再承担表达式参数状态。
- 问题：表达式主摘要沿用方向盲的 `avg_excess_residual_mean`，而 walk-forward 残差已按表达式方向调整，负向表达式会出现“顶部为负、OOS 4/4 为正”的矛盾读数；解决方案选择：主摘要展示方向残差（负向取反并标 `扣`），原始值放 tooltip，IC 与 Spread 仍保持原始值，分层表也保留原始残差并显式标注；解释：前端与后端 `validation_axis_direction_sign` 口径一致，同时不改变后端统计模型。
- 问题：表达式参数组合若默认按指标排序，用户会把“看起来最好”的参数当成系统推荐；解决方案选择：参数鲁棒性表默认按后端枚举顺序展示，点击表头才排序，样本不足的 fold 计入分母但不计为正窗口；解释：保留人工比较相邻参数的职责，避免自动挑选参数。
- 通用回测参数（指数/Beta/日期/板块/市值/最少上市日等）与格式化函数统一放在 `src/shared/backtestCommonParams.ts`、`src/shared/backtestFormat.ts`、`src/shared/expressionValidation.ts`，表达式回测页与场景/策略回测页共用同一份 `localStorage` 参数，不要各自复制表单状态。
